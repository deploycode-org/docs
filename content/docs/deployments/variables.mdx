Переменные приложения передаются в контейнер при запуске и доступны при сборке.

## Где задавать

| Уровень | Где в панели |
| --- | --- |
| Приложение | [«Архитектура»](/docs/structure/architecture#панель-сервиса) → панель сервиса → вкладка **«Переменные»**. При создании сервиса — в «Дополнительных настройках» мастера |
| Окружение | [«Окружения»](/docs/structure/environments#переменные-окружения) → «Переменные окружения», область «Окружение» |
| Проект | Там же, область **«Весь проект»** |

Имя переменной — латиница, цифры и подчёркивание, не может начинаться с цифры.

## Уровни переменных

Переменные задаются на трёх уровнях:

| Уровень | Как попадает в приложение |
| --- | --- |
| Приложение | Напрямую — каждая переменная приложения есть в контейнере |
| Окружение | Только по ссылке из переменной приложения |
| Проект | Только по ссылке из переменной приложения |

Переменные проекта и окружения — это общие значения. Сами по себе они в приложение **не попадают**:
на них нужно сослаться.

## Ссылки на переменные

В значении переменной приложения можно сослаться на другую переменную:

| Синтаксис | Откуда берётся значение |
| --- | --- |
| `${{project.KEY}}` | Переменная `KEY` проекта |
| `${{environment.KEY}}` | Переменная `KEY` окружения |
| `${{KEY}}` | Другая переменная `KEY` этого же приложения |

Например, общий адрес базы задаётся один раз в окружении, а приложения ссылаются на него:

```bash
DATABASE_URL=${{environment.DATABASE_URL}}
```

<Callout type="warn">
  Если переменной, на которую ссылается значение, не существует, деплой завершится ошибкой.
</Callout>

## Когда применяются изменения

Значения на момент запроса на деплой входят в **конфигурацию деплоя**. Изменения после этого не
влияют на уже запущенный деплой — нужен новый деплой.

## Файлы конфигурации

Передавать целые файлы конфигурации из панели пока нельзя — см.
