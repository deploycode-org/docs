---
title: Docker-контейнеры
description: Как запустить приложение в контейнере из Dockerfile или готового образа и что проверить, если он не работает.
---

Любое приложение в DeployCode работает как Docker-контейнер на вашем сервере: сервис Docker Swarm, к
которому Traefik ведёт трафик с домена. Это руководство проходит весь путь контейнера: откуда берётся образ,
как ускорить его сборку, что нужно контейнеру для работы и где искать причину, если он не запустился.

## Откуда берётся образ

| Способ | Где собирается образ | Когда подходит |
| --- | --- | --- |
| [Railpack](/docs/deployments/builders#настройки-railpack) | На сервере, без Dockerfile | Обычное приложение на Node.js, Python, Go, PHP или статический сайт, см. [Фреймворки](/docs/frameworks) |
| [Dockerfile](#сборка-по-dockerfile) | На сервере, по Dockerfile из репозитория | Нужны свой базовый образ, системные пакеты, нативные зависимости или многостадийная сборка |
| [Готовый образ](#готовый-образ) | В вашем CI или у автора приложения. DeployCode только скачивает его | Образ уже собирают и проверяют в CI: на сервер попадёт тот же образ, без второй сборки |

Между Railpack и Dockerfile выбирать заранее не нужно: если в каталоге сервиса лежит `Dockerfile`,
DeployCode собирает по нему, иначе — через Railpack, см. [Сборщик](/docs/deployments/builders#сборщик).

## Сборка по Dockerfile

<Steps>
<Step>

### Положите Dockerfile в каталог приложения

Это корень репозитория или [путь сборки](/docs/deployments/builders#путь-сборки) в монорепозитории.
Мастер на вкладке «GitHub» покажет «Обнаружено: Dockerfile». Файл с другим именем или в другом каталоге
укажите в настройках сервиса: сборщик **«Dockerfile»** и **«Путь к Dockerfile»**, например
`docker/Dockerfile.prod`. Контекст сборки — каталог сервиса.

</Step>
<Step>

### Опишите запуск в самом Dockerfile

Контейнер запускается командой из `CMD` или `ENTRYPOINT`. Команды из раздела «Сборка и запуск» в настройках
относятся только к Railpack: при сборке по Dockerfile они не применяются.

Приложение должно слушать порт из переменной `PORT` на всех интерфейсах (`0.0.0.0`): DeployCode передаёт в
`PORT` порт домена. Если в последней стадии есть `EXPOSE`, мастер подставит этот порт в настройки, см.
[Порт](/docs/frameworks#порт--главное-что-нужно-проверить).

</Step>
<Step>

### Передайте переменные сборки

Переменные с этапом **«Только сборка»** или **«Сборка и запуск»** приходят в сборку:

- обычные значения — как аргументы, объявите их через `ARG`;
- секреты, ссылки на сервисы и значения, в которых они использованы, — как секреты сборки: в образ они не
  попадают, а через `ARG` будут пустыми. Прочитайте такую переменную в шаге `RUN`:
  `RUN --mount=type=secret,id=NPM_TOKEN,env=NPM_TOKEN npm ci`.

Подробнее — в разделе [Сборка по Dockerfile](/docs/deployments/builders#сборка-по-dockerfile).

</Step>
</Steps>

Пример для приложения на Node.js:

```dockerfile title="Dockerfile"
FROM node:22 AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
RUN npm run build

FROM node:22-slim
WORKDIR /app
ENV NODE_ENV=production
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev
COPY --from=build /app/dist ./dist
EXPOSE 3000
CMD ["node", "dist/index.js"]
```

Зависимости ставятся до копирования исходного кода, поэтому правка кода не заставляет ставить их заново.
Компиляторы и dev-зависимости остаются в стадии `build` и не попадают в итоговый образ.

## Кеш сборки

Образ собирается через BuildKit, поэтому работают обычные правила кеша Docker:

- **Порядок инструкций.** Изменение в одном шаге пересобирает все шаги после него. Сначала копируйте то, что
  меняется редко (файлы зависимостей), потом исходный код.
- **`.dockerignore`.** Исключите `node_modules`, `.git` и локальные `.env`: они раздувают контекст и сбивают
  кеш при каждом изменении.
- **Монтирование кеша.** `RUN --mount=type=cache` сохраняет кеш менеджера пакетов между сборками, даже когда шаг
  выполняется заново.

Кеш хранится на сервере, где идёт сборка: на сервере развёртывания или на
[сервере сборки](/docs/deployments/build-server). На новом сервере первая сборка идёт без кеша. Если перед
сборкой на сервере [мало места](/docs/servers/requirements#диск), DeployCode чистит кеш: у сборок по
Dockerfile — целиком, у Railpack — только слои. Сбросить кеш вручную можно кнопкой **«Кеш сборок»** на
странице сервера, см. [Кеш сборки](/docs/deployments/builders#кеш-сборки).

## Готовый образ

Если образ собирает ваш CI, опубликуйте его в реестре и запустите на вкладке
[«Docker-образ»](/docs/deployments/docker-image) мастера:

- **образ** с тегом или digest, например `ghcr.io/acme/web:1.2`;
- **приватный реестр** — логин и токен только на чтение, **«Проверить доступ»** проверит вход с сервера;
- **порт веб-интерфейса** — порт, который слушает приложение в образе. `PORT` такому сервису не передаётся:
  порт выбрал автор образа.

Новую версию под тем же тегом скачивает кнопка **«Развернуть»**. Чтобы сервис обновлялся сам после
публикации, настройте [автообновление](/docs/deployments/docker-image#автообновление) — вебхук реестра или
`curl` из CI.

<Callout type="warn">
  Образ должен быть собран под архитектуру сервера — она видна в «Ресурсах сервера», в строке
  «Архитектура». Docker на Mac с Apple Silicon по умолчанию собирает образ для `linux/arm64`. Для сервера
  `x86_64` собирайте с `--platform linux/amd64`.
</Callout>

## Сеть

- **Порт.** Traefik ведёт трафик с домена на порт контейнера, указанный в домене. Приложение должно слушать
  этот порт на `0.0.0.0`: если оно слушает только `127.0.0.1`, домен вернёт 502.
- **Сервисы между собой.** Сервисы на одном сервере видят друг друга по внутренним адресам. Адрес базы
  PostgreSQL, Valkey или другого сервиса задайте переменной типа
  [«Ссылка на сервис»](/docs/deployments/variables#ссылки-на-сервисы), а не вручную. Сервисы на разных
  серверах внутренней сети не имеют и связываются только по внешнему адресу.
- **`localhost` в контейнере** — это сам контейнер. База, которая у вас на компьютере была на
  `localhost:5432`, на сервере доступна только по своему адресу.
- **Порты в обход Traefik** — для TCP и UDP вроде игровых серверов или SMTP, см. [Порты](/docs/networking/ports).

## Данные

Файловая система контейнера создаётся заново при каждом развёртывании. Загрузки пользователей, файлы SQLite и
всё, что должно пережить развёртывание, храните в [именованных томах](/docs/deployments/volumes), а данные
приложения — в [PostgreSQL](/docs/databases/postgres). Для томов есть [снимки](/docs/backups/volumes).

## Несколько контейнеров

Каждый контейнер — отдельный сервис в одном [окружении](/docs/structure/environments): приложение, база
PostgreSQL, Valkey или другой сервис из [шаблона](/docs/deployments/templates). Сервисы связываются
ссылками на сервисы, а [«Архитектура»](/docs/structure/architecture) показывает эти связи.

Поддержки Docker Compose пока нет, она появится позже. А пока разложите `docker-compose.yml` на отдельные
сервисы.

### Фоновый обработчик

Обработчику очереди или планировщику домен не нужен:

- у сервиса из готового образа выключите переключатель **HTTP** в мастере;
- у сервиса из репозитория удалите домен в разделе [«Домены»](/docs/networking). Без домена сервис не
  получает `PORT`, и панель не ждёт от него открытого порта.

Если веб-приложение и обработчик собираются из одного репозитория, создайте для обработчика второй сервис
из того же репозитория. Для Railpack задайте ему свою **«Команду запуска»**, для Dockerfile — свой
**«Путь к Dockerfile»**, например `Dockerfile.worker`.

## Ресурсы

Контейнеры пользуются CPU и памятью своего сервера. Лимиты CPU и памяти и число реплик для приложений в
панели пока не настраиваются. Загрузку видно в [«Ресурсах сервера»](/docs/servers#ресурсы-и-очистка-диска).
Если ресурсов не хватает:

- увеличьте ВМ в консоли облака;
- разнесите сервисы по разным серверам;
- вынесите сборку на [сервер сборки](/docs/deployments/build-server), чтобы она не забирала память у
  работающих приложений.

## Если контейнер не работает

Начните с журнала: на обзоре сервиса — кнопка **«Логи сборки»**, у сервиса из образа — **«Логи
развёртывания»**. Логи работающего контейнера в панели пока недоступны. Их можно посмотреть на вкладке
[«Терминал»](/docs/observability/logs#терминал-сервера) на странице сервера командой
`docker service logs <имя контейнера>`. Имя контейнера указано в настройках сервиса, в разделе «Сервис».

| Что происходит | Что проверить |
| --- | --- |
| Сборка упала | В начале журнала — какой сборщик сработал. Нехватка памяти или места, ошибки зависимостей — см. [Сборка](/docs/troubleshooting/builds) |
| Контейнер сразу завершается или перезапускается | `CMD` должен запускать процесс, который работает постоянно, а не завершается. Проверьте переменные: без нужной переменной приложение часто падает при старте |
| Сервис запущен, но домен отвечает 502 | Статус «Не отвечает на порту …» на обзоре сервиса: приложение слушает другой порт или только `127.0.0.1`. Кнопка **«Указать порт …»** переведёт адрес на открытый порт, см. [Порт](/docs/frameworks#порт--главное-что-нужно-проверить) |
| Развёртывание не становится готовым | [Healthcheck](/docs/deployments/readiness) образа не проходит или контейнер не успевает запуститься за 10 минут |
| После развёртывания пропали файлы | Они лежали вне [томов](/docs/deployments/volumes) |
| Локально работает, на сервере нет | Адреса `localhost` в переменных, переменные без этапа сборки, архитектура образа. См. [Развёртывание](/docs/troubleshooting/deployments) |
