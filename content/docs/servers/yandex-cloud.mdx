DeployCode может создать ВМ в вашем каталоге Yandex Cloud. Машина принадлежит вам, а счёт выставляет
Yandex Cloud — DeployCode не берёт комиссию. Тот же ключ сервисного аккаунта используется и для
[реестра образов](/docs/deployments/registry) Yandex Container Registry.

В панели каталог называется папкой: поле **Folder ID**, в сводке подключения — **«Папка»**.

## Подключение каталога

Понадобятся **Folder ID** каталога и **авторизованный ключ сервисного аккаунта**.

1. Скопируйте Folder ID из консоли Yandex Cloud. Можно вставить и адрес каталога целиком,
   `console.cloud.yandex.ru/folders/b1g…`: панель оставит из него только ID. Не путайте ID каталога с ID
   облака — оба начинаются с `b1g`.
2. Создайте сервисный аккаунт в этом каталоге и выдайте ему роли на каталог. Проще всего — `editor`. Или
   по минимуму:
   - для серверов — `compute.editor`, `vpc.privateAdmin`, `vpc.publicAdmin`, `resource-manager.viewer`;
   - для реестра — `container-registry.viewer`, `container-registry.images.pusher`.
3. Создайте для сервисного аккаунта авторизованный ключ: в консоли — **«Новый ключ»**.
4. В DeployCode откройте **Облачные провайдеры** и выберите Yandex Cloud в списке слева. Заполните поля и
   нажмите **«Подключить»**:

| Поле | Что вставить |
| --- | --- |
| **Folder ID** | ID каталога или его адрес в консоли |
| **Закрытый ключ** | Поле «Ваш закрытый ключ» из окна создания ключа — целиком, вместе с первой строкой `PLEASE DO NOT REMOVE THIS LINE!`. Подойдёт и скачанный JSON-файл ключа |
| **ID сервисного аккаунта** | Строка «Идентификатор» на странице сервисного аккаунта — не ID ключа. Если вставлен JSON-файл, поле скрыто: ID есть в файле |

DeployCode проверит доступ к каталогу. После сохранения ключ хранится в зашифрованном виде и больше не
показывается.

| Ошибка | Что проверить |
| --- | --- |
| Папка не найдена | Folder ID |
| Это ID облака, а не папки | Панель перечислит каталоги этого облака с их ID — вставьте нужный |
| У сервисного аккаунта нет доступа к этой папке | Роли сервисного аккаунта на каталог |
| Yandex Cloud не принял ключ | Ключ отозван или ID сервисного аккаунта — не того аккаунта, которому принадлежит ключ |
| Это открытый ключ | Нужен закрытый — поле «Ваш закрытый ключ» в том же окне |
| Это ID ключа, а не сервисного аккаунта | ID аккаунта — на его странице, в строке «Идентификатор» |

OAuth-токены Яндекс ID не поддерживаются — нужен именно ключ сервисного аккаунта.

Ключ подключённого каталога можно заменить: вставьте новый в блоке **«Ключ сервисного аккаунта»** и нажмите
**«Сохранить ключ»**.

### Проверка подключения

Когда вы открываете Yandex Cloud в облачных провайдерах, панель проверяет, работает ли сохранённый ключ и
может ли сервисный аккаунт видеть машины в каталоге. Если нет, над сводкой видна причина и что сделать:

| Сообщение | Что сделать |
| --- | --- |
| «Yandex Cloud не принимает ключ DeployCode: сервисный аккаунт удалён или ключ отозван» | Загрузите ключ нового сервисного аккаунта. В сводке — **«Ключ сервисного аккаунта: Не принят»** |
| «Сервисному аккаунту DeployCode не хватает прав в папке Yandex Cloud» | Выдайте ему роль `editor` на каталог в консоли Yandex Cloud |

В обоих случаях у провайдера статус **«Не работает»**, в списке провайдеров он отмечен красной точкой, а в
мастере нового сервера Yandex Cloud выбрать нельзя: подсказка на карточке называет причину, ссылка
**«Исправить подключение»** ведёт сюда. Если Yandex Cloud просто не ответил, панель предупредит
«Yandex Cloud не ответил: …», но заказывать ВМ не запретит.

Права на публичные адреса (`vpc.publicAdmin`) заранее проверить нельзя: их нехватка видна только при заказе.

### Отключение

**«Отключить провайдера»** удаляет привязку каталога и ключ сервисного аккаунта: создать новые ВМ и подключить
реестры Yandex Cloud не получится. Серверы и подключённые реестры останутся, но для операций с образами
придётся снова настроить ключ. Окно подтверждения перечисляет серверы, заказанные в Yandex Cloud: после
отключения панель не сможет удалить их ВМ, повторить автонастройку и сверять их с облаком. Удалять такие ВМ
придётся в консоли Yandex Cloud.

## Создание сервера

**Добавить сервер → Yandex Cloud**, затем:

<Steps>
<Step>

### Назначение

Тип сервера и нагрузка выбираются так же, как для
[reg.ru Cloud](/docs/servers/regru-cloud#создание-сервера), и по нагрузке подбирается конфигурация. На карточке нагрузки видно, какую ВМ получит
сервер развёртывания:

| Нагрузка | ВМ |
| --- | --- |
| Pet-проект | 2 vCPU с гарантированной долей 50%, 4 ГБ |
| Стартап (по умолчанию) | 2 vCPU, 4 ГБ |
| Прод-нагрузка | 4 vCPU, 8 ГБ |
| Другое | Конфигурация выбирается вручную |

Меньше 2 vCPU в Yandex Cloud не бывает, поэтому pet-проект отличается от стартапа долей vCPU: такая ВМ
дешевле, но сборки на ней идут медленнее. Сервер сборки и все остальные нагрузки получают полные ядра.

</Step>
<Step>

### Регион и ОС

| Параметр | Варианты |
| --- | --- |
| Зона доступности | `ru-central1-a` (по умолчанию), `ru-central1-d`, `ru-central1-e` — все в Москве |
| Конфигурация | От 2 vCPU / 2 ГБ до 8 vCPU / 16 ГБ на платформе Intel Ice Lake (`standard-v3`). Автоматически подбираются только конфигурации от 4 ГБ, остальные — в варианте «Другое» |
| Диск SSD | 10, 20, 40 (по умолчанию) или 80 ГБ |
| Образ ОС | Ubuntu 22.04 LTS (по умолчанию) или 20.04 LTS |

Зону `ru-central1-b` мастер пока не предлагает: Yandex Cloud закрыл её для новых ресурсов.

Квота облака на SSD в зоне бывает меньше 40 ГБ: у нового облака это часто 10 ГБ. Диск больше квоты Yandex
Cloud не создаст. Квоты смотрят в консоли: облако → «Квоты» → Compute Cloud. На диске меньше 40 ГБ мастер
предупредит, что кеш и промежуточные слои сборок могут быстро занять всё место.

</Step>
<Step>

### Подтверждение

Укажите название и принадлежность сервера и нажмите **«Создать ВМ»**. Как и для reg.ru Cloud, шаг заранее
перечисляет прошлые заказы, которые не настроились: их ВМ продолжают тарифицироваться.

В сводке справа — примерная стоимость в месяц, **«≈ … / мес»**. Она посчитана по текущим тарифам Yandex
Cloud с НДС за 30 дней: vCPU с выбранной долей, память, SSD выбранного размера и публичный адрес. Счёт
выставит Yandex Cloud.

</Step>
</Steps>

Если Yandex Cloud отклонил заказ, в панели ничего не появляется, а мастер называет причину:
ключ не принят, не хватает прав, не хватает квоты (мастер назовёт размер диска, который не поместился) или
зона закрыта для новых ресурсов. Сеть и подсеть, созданные для такого заказа, удаляются.

## Что появится в каталоге

| Ресурс | Как выглядит в консоли |
| --- | --- |
| ВМ | Имя — название сервера латиницей со случайным хвостом, например `production-msk-01-3fa9c2`. Если название не начинается с латинской буквы, впереди будет `dc-`, а если в нём нет ни латиницы, ни цифр — `deploycode-…`. Описание — `DeployCode: <название>`, метка `managed-by=deploycode` |
| Сеть | `deploycode-network` с меткой `managed-by=deploycode`. Создаётся при первом заказе, следующие ВМ попадают в неё же |
| Подсеть | `deploycode-subnet-<зона>`, по одной на зону: `10.10.0.0/24` в `ru-central1-a`, `10.10.3.0/24` в `ru-central1-d`, `10.10.4.0/24` в `ru-central1-e` |
| Диск | Загрузочный диск SSD (`network-ssd`) выбранного размера. Удаляется вместе с ВМ |
| Адрес | Публичный IPv4 |

Подключение идёт под пользователем `ubuntu`: DeployCode передаёт свой ключ в метаданных ВМ, а установку
выполняет через sudo.

Квота облака на число сетей невелика. Если квоты на ещё одну сеть не осталось, ВМ создаётся в подсети одной из
уже существующих сетей каталога в этой зоне, в первую очередь сети `default`. Мастер и строка **«Сеть»** на
странице сервера предупреждают, что эта сеть общая с другими машинами каталога. Если подходящей подсети в
зоне нет, заказ отклоняется с сообщением о квоте.

## Настройка после создания

Когда облако выдаст машине IP-адрес и SSH станет доступен, DeployCode сам настроит сервер: установит
Docker, Swarm, Traefik, Railpack и остальные компоненты, как при [подключении своего
сервера](/docs/servers/connect#настройка-сервера). Страницу можно закрыть: создание и настройка
продолжатся в фоне. Кнопка **«Открыть карточку сервера»** на шаге **«Установка»** доступна сразу, как
только сервер появился в панели.

| Статус в карточке | Что происходит |
| --- | --- |
| Подключается | Yandex Cloud создаёт ВМ, плитка **«Подключение»** — «Создаётся в облаке» |
| Устанавливается | DeployCode ставит компоненты на ВМ |
| Работает | Сервер готов к развёртываниям |
| Ошибка | Создание или настройка не удались, причина — над вкладками |

Пока настройка идёт, развёртывания и действия с PostgreSQL на сервере недоступны. Журнал установки
сохраняется во вкладке [«Активность»](/docs/servers#логи-установки).

### Если заказ ещё идёт

Если заказать вторую ВМ, пока первая не настроена, придётся платить за обе. Поэтому шаг **«Сервер»** в мастерах нового
проекта и сервиса показывает «Сервер „…“ ещё создаётся» и кнопку **«Следить за созданием»**. Если готовых
серверов нет, встроенный мастер сразу открывается на ходе этого заказа — и после перезагрузки страницы тоже.

### Если настройка не удалась

Причина видна на шаге **«Установка»** мастера и в карточке сервера:

| Сообщение | Что сделать |
| --- | --- |
| «Сервер остановлен в Yandex Cloud» | Запустите ВМ в консоли и повторите автонастройку |
| «Сервер удалён в Yandex Cloud» | Удалите сервер из DeployCode и создайте новый |
| «Облако не подтвердило готовность сервера за 20 минут» | Проверьте ВМ в консоли Yandex Cloud |
| «Не удалось подключиться к облачному серверу… Последняя ошибка: …» | За 20 минут панель не связалась с провайдером или с ВМ по SSH. Проверьте доступ к ним, затем повторите |
| «Yandex Cloud не принимает ключ DeployCode…», «…не хватает прав в папке Yandex Cloud» | См. [Проверка подключения](#проверка-подключения), затем повторите |
| «Настройка сервера не завершена: …» | Установка на ВМ упала. Исправьте причину по [журналу установки](/docs/servers#логи-установки) |

Остановленную или удалённую ВМ панель замечает сразу, не дожидаясь 20 минут.

В карточке сервера под причиной две кнопки:

- **«Повторить автонастройку»** — начинает заново: ждёт ВМ ещё до 20 минут, затем ставит компоненты. Её видят
  пользователи с правом создавать серверы;
- **«Удалить сервер и ВМ»** — открывает [удаление сервера](/docs/servers#удаление-сервера) с уже отмеченным
  удалением ВМ. Её видят пользователи с правом удалять серверы. Эта же кнопка есть на шаге
  **«Установка»** мастера: после удаления он вернётся к выбору облака с прежними настройками.

ВМ, которая не настроилась, продолжает работать и тарифицироваться в Yandex Cloud, пока её не удалить.

Проверить установленные компоненты можно во вкладке [«Проверка»](/docs/servers/connect#проверка-готовности).

## Удаление сервера

В окне удаления сервера, созданного из панели, отмечено **«Удалить ВМ в Yandex Cloud»**: ВМ и её диск
удаляются без возможности восстановления. Снимите отметку, чтобы оставить машину. Если Yandex Cloud не дал
удалить ВМ, например, ключ уже не принимается, сервер всё равно уйдёт из DeployCode, а ВМ придётся удалить в
консоли. Подробнее — в разделе [Удаление сервера](/docs/servers#удаление-сервера).

Если машину удалили в консоли, DeployCode заметит это при проверке доступности и пометит сервер
**«Удалён у провайдера»**.
